# M2 data shell

The only authoritative application database client is `shared/server/database.mjs`. `DATABASE_MODE` is `local` or `production`; `DATABASE_URL` and `DATABASE_EXPECTED_NAME` are required. Production also requires `DATABASE_EXPECTED_HOST` and a URL with `sslmode=verify-full`. The client config enables certificate verification and checks the expected host and database before connecting. Local mode accepts only a loopback host. These names are server-only; never prefix them with `NEXT_PUBLIC_` or commit their values.

Run `node scripts/m2-migrate.mjs` from a server/operator environment before routing traffic to the application. It reads the ordered SQL files in `migrations/`, takes a transaction-scoped advisory lock for each migration (safe with Neon transaction pooling), applies each version transactionally, verifies checksums on repeat, and reports only database name, server version, and applied versions. A missing secret, wrong target, unsafe TLS or failed SQL exits nonzero with a redacted code. The current inventory is `0001_schema_migrations.sql`, which creates only the migration ledger. T04 owns identity/session migrations.

The Next `instrumentation.ts` startup hook uses the same client and requires migration `0001` whenever `DATABASE_MODE` is set or `VERCEL_ENV=production`. It fails startup without echoing a credential if configuration, connection, or migration state is invalid. The deployed `GET /api/system/database` route independently checks readiness and returns `ready` with a redacted state or HTTP 503. It is a deployment/operations probe and exposes no credential. A production deployment must set the three additional named environment references alongside T01's `DATABASE_URL`, run migration `0001` against the named Neon database, then request this endpoint. This route is not an authentication or domain-data endpoint.

Run `node scripts/m2-data-evidence.mjs` after a production build for a fresh disposable PostgreSQL 18.7 Compose database. It checks pre-migration emptiness, applies and repeats the migration, compares tables/columns/keys with the ERD, creates and removes an isolated test schema, requests the built Next server's database route, and removes the Compose volume. It uses random local credentials only in memory. No test seed SQL enters the intended migration directory.
